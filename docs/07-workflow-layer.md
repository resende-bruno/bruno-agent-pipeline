# 07 - Workflow layer

Everything up to here is plumbing. This layer is the *method*: the collaboration habits that
make agent-assisted feature work actually converge. Mine came from months of desk-side work with
a coding agent on a large production codebase; porting the pipeline meant writing those habits
down and teaching them to the gateway. Adopt what fits, rewrite the rest, but write yours down:
an undocumented workflow can't be followed by an agent, and "the agent decides how we work" is
the wrong default.

## The lifecycle (vocabulary, not law)

For substantial features, work moves through named stages, **each one its own dispatch** (or a
few), each with a natural model tier:

| Stage | Tier | What it produces |
|---|---|---|
| 1. Brainstorm | planning | the idea explored: options, trade-offs, no code |
| 2. Scope review | planning | the idea checked against the *real* code: assumptions verified, corrections reported |
| 3. Phased plan | planning | a written plan split into independently dispatchable phases; open decisions extracted as numbered questions for the human |
| 4. Pressure-test | planning | optional: the plan run through a multi-model review for blind spots |
| 5. Phase 1..N | impl | one dispatch per phase, in order; each ends with the mandatory finish-up (below) |
| 6. Review passes | impl/quick | the named review dispatches (below), whichever you pick |
| 7. Test list | planning | an exhaustive manual-test scenario list; generation only |
| 8. Closeout | quick | notes consolidated, project skills updated, branch handed to the human |

The crucial rule, stated verbatim in the gateway's manual: **the human decides which stages a
given piece of work deserves.** A bug fix is a single `quick` dispatch; a cross-cutting feature
may use all eight. The gateway never refuses or stalls because a stage was skipped. At most it
suggests one, in a single line, when skipping carries real risk. Lifecycles that enforce
themselves become bureaucracy; lifecycles that exist as shared vocabulary become speed.

Progress tracking is just the `next dispatch:` pointer in the project's NOTES.md
([06](06-memory.md)). Each stage's prompt tells the agent to record what finished and what comes
next, so any future dispatch (or a different human) can pick up the thread.

## Echo-back: making the gateway understand before it dispatches

For a **new feature idea or scope change**, the gateway doesn't draft a prompt. It first
restates the idea in its own words (what it understood, what it's assuming) plus numbered
clarifying questions, and waits. Only after your answers does it produce the improved prompt for
confirmation. Why the extra round-trip: on a phone you type shorthand, and the costliest failure
is a well-executed dispatch of the wrong idea. Continuations ("start phase 3", a named review, a
fix on known code) skip echo-back entirely; it must never slow the fast path.

## Named review dispatches

Three canned reviews the gateway holds as ready prompts, so a two-word message from the phone
triggers a full pass. All three are **findings-only**: they change no code; fixes are their own
dispatches after you've read the findings:

- **Quality review**: the branch diff line by line, four fixed questions in order: is it
  optimized? is it secure? is it over-coded, i.e. same result with less code? does it match what
  was asked and planned (checked against NOTES.md)? Every finding reported, including
  low-severity and uncertain ones, confidence noted.
- **Pattern alignment**: does the new code match the project's own conventions (naming,
  structure, idioms)? Each deviation must cite the existing `file:line` showing the pattern it
  should follow. A convention claim without an in-repo citation is just taste.
- **Blast-radius audit**: check the change against documented context *outside* the feature
  (shared tables, duplicated logic, cross-module flows, whatever your project documents as
  module boundaries) and report anything the diff could break elsewhere.

## Test lists: generated by the agent, executed by the human

When a feature is implemented, a `planning` dispatch generates an **exhaustive manual-test
scenario list**: every possible usage *including wrong usage* (invalid input, out-of-order
actions, permission edges, concurrency), double-checked against the actual diff for missing
cases, with open product questions extracted and numbered. The list is delivered in the output
and persisted to NOTES.md.

Hard boundary: the agent **never executes the tests**. No browsers, no running app, no test
clicks. Execution is where human judgment and real-environment access live; the agent's
comparative advantage is completeness of the list, not operation of the app.

## The mandatory finish-up (implementation dispatches)

Every implementation dispatch ends with a self-pass over **its own diff**, defined once in the
memory repo's conventions ([template](../templates/memory-repo/_shared/CLAUDE.md)) so no prompt
has to repeat it:

1. **Comment hygiene**: strip comments a competent reader doesn't need; keep only constraints
   the code can't show.
2. **Code cleaning**: dead code, unused imports, leftover scaffolding from its own work.
3. **Optimization**: obvious waste in the touched paths.
4. **Security**: injection, unvalidated input at trust boundaries, permission gaps in the
   touched paths.
5. **Over-coding**: can the same result be achieved with less code? Simplify where yes.

The output ends with one line per check: found-and-changed, or "nothing". This is a self-pass
over one dispatch's diff; it complements the branch-wide named reviews, not replaces them. And
deliberately absent: commit messages. The agent doesn't write them because the agent doesn't
commit. Describing the change is part of the human's review.

## ⚠ Decisions you must make

1. Which lifecycle stages exist in *your* vocabulary, and their tier mapping. Start from this
   table, delete what you won't use.
2. Your named reviews. The three above assume a conventions-heavy production codebase; a
   greenfield solo project might want a different set.
3. Your finish-up checklist: the five checks above, minus/plus what your stack needs
   (accessibility, i18n, migration safety...).
4. Where your human-only line sits. Mine: commits, merges, DB changes, test *execution*. Yours
   may differ, but draw it explicitly, in writing, in the gateway's manual and the memory
   conventions, so neither agent ever has to guess.
